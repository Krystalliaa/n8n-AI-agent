# Writing Style Guide

## Purpose

This repository documents real projects built for learning, experimentation, automation, and portfolio development.

Documentation must demonstrate technical understanding rather than marketing language.

---

## Writing Style

Always write in first person.

Good:

"I deployed Splunk to centralize log collection."

Bad:

"Splunk was deployed to centralize log collection."

---

## Documentation Goals

Every project should answer:

1. What problem was I solving?
2. Why did I choose these technologies?
3. How did I implement the solution?
4. What challenges did I encounter?
5. How did I solve them?
6. What did I learn?
7. What would I improve next?

---

## Never Invent Information

Never create:

* screenshots
* logs
* test results
* errors
* configurations
* architecture decisions

If information is missing, use:

[TO BE DOCUMENTED]

---

## Required Sections

Every project must contain:

# Project Title

## Introduction

## Objectives

## Technologies Used

## Architecture Overview

## Implementation Process

## Challenges Encountered

## Troubleshooting

## Lessons Learned

## Future Improvements

---

## Lessons Learned Rules

Lessons Learned must contain practical technical knowledge gained while building the project.

Avoid generic statements.

Bad:

"I learned a lot."

Good:

"I learned how Active Directory DNS configuration directly impacts domain join operations."

---

## Troubleshooting Rules

Only document issues explicitly provided by the user.

Never invent troubleshooting content.

---

## Portfolio Focus

Documentation should demonstrate:

* cybersecurity skills
* automation skills
* troubleshooting ability
* infrastructure knowledge
* system design thinking
* continuous learning
* project ownership
